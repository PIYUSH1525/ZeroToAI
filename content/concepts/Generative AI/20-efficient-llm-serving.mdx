    <div className="space-y-6 text-[16px] leading-8 text-slate-300">

Serving well means answering <strong className="text-white">fast</strong>, serving <strong className="text-white">many people per GPU</strong> and keeping the <strong className="text-white">cost per token</strong> low.

  <section>
    <h2 className="mb-6 border-l-4 border-violet-500 pl-4 text-2xl font-bold tracking-tight text-white sm:text-3xl">
      2. Beginner: Prefill and Decode
    </h2>
    <div className="space-y-6 text-[16px] leading-8 text-slate-300">
      <div>
        Every request has two phases with very different behavior:
      </div>
      <div className="grid gap-5 md:grid-cols-2">
        <div className="rounded-xl border border-blue-500/25 bg-blue-500/[0.04] p-6">
          <div className="mb-1 flex items-center justify-between">
            <span className="font-bold text-blue-300">Prefill</span>
            <span className="rounded bg-blue-950/80 px-2 py-0.5 font-mono text-xs text-blue-300">Read the prompt</span>
          </div>
          <div className="mt-2 space-y-2 text-xs leading-relaxed text-slate-300">
            <div><strong className="text-white">What:</strong> Process all prompt tokens at once and fill the KV cache.</div>
            <div><strong className="text-white">Bottleneck:</strong> <strong className="text-white">Compute</strong>. Big parallel matrix math keeps the GPU busy.</div>
            <div><strong className="text-white">User feels:</strong> Time to first token</div>
          </div>
        </div>
        <div className="rounded-xl border border-emerald-500/25 bg-emerald-500/[0.04] p-6">
          <div className="mb-1 flex items-center justify-between">
            <span className="font-bold text-emerald-300">Decode</span>
            <span className="rounded bg-emerald-950/80 px-2 py-0.5 font-mono text-xs text-emerald-300">Write the answer</span>
          </div>
          <div className="mt-2 space-y-2 text-xs leading-relaxed text-slate-300">
            <div><strong className="text-white">What:</strong> Generate one token at a time, reading the whole model and the cache for each token.</div>
            <div><strong className="text-white">Bottleneck:</strong> <strong className="text-white">Memory bandwidth</strong>. Little math per byte moved.</div>
            <div><strong className="text-white">User feels:</strong> Streaming speed</div>
          </div>
        </div>
      </div>
      <div className="rounded-xl border border-amber-500/20 bg-amber-500/[0.05] p-5 text-sm leading-relaxed">
        <strong className="text-amber-300">Why this matters:</strong> Decode is slow because the GPU spends most of its time <em>loading weights from memory</em> to produce a single token. Anything that lets one weight load serve <strong className="text-white">more tokens</strong> speeds things up a lot.
      </div>
    </div>
  </section>

  <section>
    <h2 className="mb-6 border-l-4 border-emerald-500 pl-4 text-2xl font-bold tracking-tight text-white sm:text-3xl">
      3. Medium: Batching and Continuous Batching
    </h2>
    <div className="space-y-6 text-[16px] leading-8 text-slate-300">
      <div>
        Because loading the weights is the expensive part, serving <strong className="text-white">many requests together</strong> is nearly free per request: one trip to memory feeds a whole batch of tokens. That is <strong className="text-white">batching</strong>.
      </div>
      <div>
        But requests finish at different times. With <strong className="text-white">static batching</strong>, the whole batch waits for its longest request, and short requests leave slots empty. With <strong className="text-white">continuous batching</strong> (also called in-flight batching), the moment a request finishes, a waiting request takes its slot, so the GPU stays busy.
      </div>
      <div className="overflow-x-auto rounded-2xl border border-white/10">
        <table className="w-full text-left text-sm">
          <thead className="bg-white/[0.04] text-xs uppercase tracking-wider text-slate-400">
            <tr>
              <th className="px-5 py-3"></th>
              <th className="px-5 py-3">Static batching</th>
              <th className="px-5 py-3">Continuous batching</th>
            </tr>
          </thead>
          <tbody className="divide-y divide-white/5 text-slate-300">
            <tr><td className="px-5 py-3 font-semibold text-white">Slot freed when a request ends</td><td className="px-5 py-3">Stays empty until the whole batch ends</td><td className="px-5 py-3">Immediately refilled from the queue</td></tr>
            <tr><td className="px-5 py-3 font-semibold text-white">GPU utilization</td><td className="px-5 py-3">Low and uneven</td><td className="px-5 py-3">High</td></tr>
            <tr><td className="px-5 py-3 font-semibold text-white">Short requests</td><td className="px-5 py-3">Wait for long ones</td><td className="px-5 py-3">Leave right away</td></tr>
          </tbody>
        </table>
      </div>
      <div className="rounded-xl border border-emerald-500/20 bg-emerald-500/[0.05] p-5 text-sm leading-relaxed">
        <strong className="text-emerald-300">Result:</strong> In the simulation below, continuous batching keeps the GPU about 80% busy versus about 60% for static batching, finishing the same work in fewer steps.
      </div>
    </div>
  </section>

  <section>
    <h2 className="mb-6 border-l-4 border-orange-500 pl-4 text-2xl font-bold tracking-tight text-white sm:text-3xl">
      4. Medium: PagedAttention and Prefix Caching
    </h2>
    <div className="space-y-6 text-[16px] leading-8 text-slate-300">
      <div>
        Each request needs a KV cache, and its final length is not known in advance. A naive server <strong className="text-white">reserves the maximum length</strong> for every request, wasting most of the memory.
      </div>
      <div>
        <strong className="text-white">PagedAttention</strong> (introduced by the vLLM project) stores the cache in small fixed-size <strong className="text-white">pages</strong>, allocated only as needed, like virtual memory in an operating system. Little memory is wasted, so many more requests fit on the same GPU.
      </div>
      <div className="rounded-xl border border-blue-500/20 bg-blue-500/[0.05] p-5 text-sm leading-relaxed">
        <strong className="text-blue-300">Prefix caching:</strong> If many requests start with the same system prompt, their first pages of the cache are identical and can be <strong className="text-white">shared</strong> instead of recomputed, which cuts both time and memory.
      </div>
      <div className="rounded-xl border border-white/10 bg-white/[0.03] p-5">
        <div className="mb-2 font-bold text-white">Quantization helps too</div>
        <div className="text-sm leading-relaxed text-slate-300">Smaller weights (8-bit, 4-bit) mean fewer bytes to load per token, which directly speeds up memory-bound decoding. Quantizing the KV cache lets even more requests fit.</div>
      </div>
    </div>
  </section>

  <section>
    <h2 className="mb-6 border-l-4 border-cyan-500 pl-4 text-2xl font-bold tracking-tight text-white sm:text-3xl">
      5. Advanced: Speculative Decoding
    </h2>
    <div className="space-y-6 text-[16px] leading-8 text-slate-300">
      <div>
        Decode produces one token per expensive pass. <strong className="text-white">Speculative decoding</strong> uses a small, fast <strong className="text-white">draft model</strong> to guess the next few tokens (for example 4), then asks the big model to <strong className="text-white">check all of them in a single pass</strong>. The big model keeps the correct prefix and fixes the first mistake.
      </div>
      <div className="rounded-xl border border-white/10 bg-[#060913] p-5 text-center text-white">
        $$\text{expected tokens per big-model step} = \frac{1 - \alpha^{k+1}}{1 - \alpha}$$
      </div>
      <div>
        Here $\alpha$ is the chance that the big model accepts a drafted token and $k$ is how many tokens are drafted. The final answer has <strong className="text-white">exactly the same quality</strong> as running the big model alone, because the big model verifies everything.
      </div>
      <div className="overflow-x-auto rounded-2xl border border-white/10">
        <table className="w-full text-left text-sm">
          <thead className="bg-white/[0.04] text-xs uppercase tracking-wider text-slate-400">
            <tr>
              <th className="px-5 py-3">Accept rate α</th>
              <th className="px-5 py-3">Tokens per big step (k = 4)</th>
            </tr>
          </thead>
          <tbody className="divide-y divide-white/5 text-slate-300">
            <tr><td className="px-5 py-3 font-semibold text-white">0.6</td><td className="px-5 py-3">about 2.3</td></tr>
            <tr><td className="px-5 py-3 font-semibold text-white">0.8</td><td className="px-5 py-3">about 3.4</td></tr>
            <tr><td className="px-5 py-3 font-semibold text-white">0.9</td><td className="px-5 py-3">about 4.1</td></tr>
          </tbody>
        </table>
      </div>
      <div className="rounded-xl border border-amber-500/20 bg-amber-500/[0.05] p-5 text-sm leading-relaxed">
        <strong className="text-amber-300">Trade-off:</strong> It needs an extra draft model and works best when the draft often agrees with the big model, for example on predictable text such as code.
      </div>
    </div>
  </section>

    <h2 data-type="code" className="mb-6 border-l-4 border-teal-500 pl-4 text-2xl font-bold tracking-tight text-white sm:text-3xl">
      7. Python Implementation: Batching, Speculative Decoding and Paged Memory
    </h2>
    <div className="space-y-6 text-[16px] leading-8 text-slate-300">
      <div>
        This script simulates 32 requests of random length on a GPU with 8 slots under static and continuous batching, calculates the expected speed-up of speculative decoding, and compares reserving the maximum cache length against paging.
      </div>
      <div className="overflow-hidden rounded-2xl border border-white/10 bg-[#060911]">
        <div className="flex items-center justify-between border-b border-white/10 bg-white/[0.03] px-5 py-3">
          <span className="font-mono text-xs font-semibold text-teal-400">serving_simulation.py</span>
          <span className="font-mono text-[11px] text-slate-400">Python 3.10+ · NumPy only</span>
        </div>
        <pre className="overflow-x-auto p-6 font-mono text-sm leading-7 text-slate-200">
          <code>
            <span className="block">import numpy as np</span>
            <span className="block">&nbsp;</span>
            <span className="block text-slate-500"># 1. Static vs continuous batching</span>
            <span className="block">rng = np.random.default&#95;rng(0)</span>
            <span className="block">lengths = rng.integers(10, 200, size=32)                 # how many tokens each request will generate</span>
            <span className="block">slots = 8                                                # requests the GPU can handle at once</span>
            <span className="block">&nbsp;</span>
            <span className="block text-cyan-300">def static&#95;batching(lengths, slots):</span>
            <span className="block">    steps = 0</span>
            <span className="block">    for i in range(0, len(lengths), slots):</span>
            <span className="block">        steps += lengths&#91;i:i + slots&#93;.max()              # the whole batch waits for its longest request</span>
            <span className="block">    return steps</span>
            <span className="block">&nbsp;</span>
            <span className="block text-cyan-300">def continuous&#95;batching(lengths, slots):</span>
            <span className="block">    queue = list(lengths)</span>
            <span className="block">    running, steps = &#91;&#93;, 0</span>
            <span className="block">    while queue or running:</span>
            <span className="block">        while queue and len(running) &lt; slots:            # refill a slot the moment one frees up</span>
            <span className="block">            running.append(queue.pop(0))</span>
            <span className="block">        steps += 1</span>
            <span className="block">        running = &#91;r - 1 for r in running if r - 1 &gt; 0&#93;</span>
            <span className="block">    return steps</span>
            <span className="block">&nbsp;</span>
            <span className="block">useful = int(lengths.sum())</span>
            <span className="block">s, c = static&#95;batching(lengths, slots), continuous&#95;batching(lengths, slots)</span>
            <span className="block">print(&quot;Useful tokens to generate:&quot;, useful)</span>
            <span className="block">print(&quot;Static batching steps:&quot;, int(s), &quot;| GPU busy&quot;, round(100 &#42; useful / (s &#42; slots)), &quot;%&quot;)</span>
            <span className="block">print(&quot;Continuous batching steps:&quot;, int(c), &quot;| GPU busy&quot;, round(100 &#42; useful / (c &#42; slots)), &quot;%&quot;)</span>
            <span className="block">&nbsp;</span>
            <span className="block text-slate-500"># 2. Speculative decoding: a small model drafts k tokens, the big model checks them at once</span>
            <span className="block text-cyan-300">def expected&#95;tokens&#95;per&#95;step(accept&#95;rate, k):</span>
            <span className="block">    return (1 - accept&#95;rate &#42;&#42; (k + 1)) / (1 - accept&#95;rate)</span>
            <span className="block">&nbsp;</span>
            <span className="block">for a in &#91;0.6, 0.8, 0.9&#93;:</span>
            <span className="block">    print(&quot;accept rate&quot;, a, &quot;| draft 4 tokens -&gt; about&quot;, round(expected&#95;tokens&#95;per&#95;step(a, 4), 2), &quot;tokens per big-model step&quot;)</span>
            <span className="block">&nbsp;</span>
            <span className="block text-slate-500"># 3. Paged KV cache: memory wasted by reserving the maximum length for every request</span>
            <span className="block">max&#95;len, page = 4096, 16</span>
            <span className="block">used = rng.integers(50, 1500, size=100)</span>
            <span className="block">reserved = len(used) &#42; max&#95;len</span>
            <span className="block">paged = int(np.sum(np.ceil(used / page) &#42; page))</span>
            <span className="block">print(&quot;Reserved up front:&quot;, format(reserved, &quot;,&quot;), &quot;token slots | paged:&quot;, format(paged, &quot;,&quot;), &quot;token slots&quot;)</span>
          </code>
        </pre>
      </div>
      <div className="rounded-xl border border-emerald-500/20 bg-emerald-500/[0.05] p-5">
        <div className="mb-2 font-mono text-xs font-bold text-emerald-300">EXPECTED OUTPUT (your numbers may differ slightly)</div>

          <div>Static batching steps: 724 | GPU busy 61 %</div>
          <div>Continuous batching steps: 533 | GPU busy 82 %</div>
